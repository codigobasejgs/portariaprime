01 Resumo executivo

O sistema funciona como demonstração e falha como sistema de custódia. A interface está bem construída e o fluxo operacional é coerente — mas não existe controle de acesso em nenhuma camada, e as garantias que o sistema exibe na tela (notificação enviada, encomenda registrada, assinatura coletada) não correspondem, em vários caminhos, ao que de fato aconteceu.

Três conclusões independentes sustentam a reprovação:

1. O banco está aberto à internet. Todas as seis tabelas têm política FOR ALL USING (true) e a chave anônima está — corretamente, por design do Vite — dentro do bundle público. Isso significa que qualquer pessoa com o endereço do site lê, altera e apaga qualquer registro. Confirmei isso executando as operações, não deduzindo: apaguei uma linha de auditoria que eu mesmo criei, e li os hashes de senha das contas de portaria e síndico.

2. A autenticação é decorativa. Abrir villageazaleia.vercel.app/?role=sindico entrega o painel administrativo completo, sem senha. O mesmo parâmetro entra como qualquer morador escolhido — e esse link, com ?role=morador, é enviado dentro de toda mensagem de WhatsApp e e-mail que o sistema dispara.

3. O sistema afirma fatos que não verifica. O toast de sucesso do registro é disparado antes das requisições terminarem. O log permanente de auditoria grava "Disparo Multicanal: 2 WhatsApp(s), E-mail Resend e Web Push" contando tentativas, não entregas. Uma falha real de e-mail é registrada como SIMULATED — a mesma palavra usada para teste local. Numa disputa sobre encomenda extraviada, o síndico leria essa trilha como prova de que o morador foi avisado.

Circunstância atenuante relevante: a base de produção está praticamente vazia hoje — 1 unidade cadastrada, 2 contas de staff, 0 encomendas. A exposição real de dados pessoais neste momento é mínima. A janela para corrigir antes da operação começar está aberta, e é isso que torna esta auditoria útil em vez de tardia.

04 Bugs críticos

BUG-001 Crítico Segurança · Banco

Banco inteiro legível, editável e apagável por qualquer pessoa

ProblemaAs seis tabelas têm política FOR ALL USING (true) WITH CHECK (true) (schema.sql:146-162). A chave anônima está no bundle público — o que é correto desde que o RLS restrinja. Como não restringe, essa chave equivale a credencial de leitura e escrita irrestrita.

CausaPolíticas de desenvolvimento levadas para produção sem substituição por regras ancoradas em identidade.

Evidência — sonda executada contra produção

1) INSERT anonimo em activity_logs -> HTTP 201 2) UPDATE anonimo (adulterar trilha) -> HTTP 204 3) DELETE anonimo (apagar trilha) -> HTTP 204 4) Limpeza confirmada (linha removida) -> SIM 5) SELECT anonimo staff_accounts -> HTTP 200 | contas expostas: 2 | hash legivel: SIM 6) SELECT anonimo units (dados pessoais)-> HTTP 200 | moradores expostos: 1

A linha usada no teste foi criada e removida por mim; nenhum dado preexistente foi tocado. O passo 5 é o mais grave: com o hash de síndico em mãos e o algoritmo público (auth.service.ts:12, SHA-256 com salt global fixo), a senha cai em segundos — ou o atacante simplesmente grava um hash próprio via UPDATE e passa a logar legitimamente.

CorreçãoSubstituir as políticas por regras baseadas em auth.uid(); staff_accounts não deve ser legível por anon em hipótese alguma; migrar autenticação para Supabase Auth. Rotacionar as senhas de staff depois.

ResultadoFAIL — confirmado empiricamente.

BUG-002 Crítico Autenticação

Parâmetro de URL concede sessão de síndico sem senha

ProblemaApp.tsx:189-208 lê ?role= e cria a sessão sem qualquer credencial. ?role=sindico abre o painel administrativo; ?role=morador&unit=B05-A304 entra como aquele morador específico.

AgravanteEsse link é embutido em toda mensagem enviada — evolution-whatsapp.ts:21 e resend-email.ts:36 montam ${origin}?unit=${pkg.unitId}&role=morador. Basta trocar o valor de unit para ver as encomendas, fotos e QR Codes de outro apartamento.

Agravante 2O efeito depende de [units, staffAccounts], então re-executa a cada sincronização — o logout não segura enquanto o parâmetro estiver na URL.

CorreçãoRemover o bloco. Era atalho de desenvolvimento que foi para produção; o custo de remoção é de poucas linhas.

ResultadoFAIL — análise estática (o alvo Vercel está inacessível desta rede; ver §9).

BUG-003 Crítico Fluxo 5 · Retirada

Retirada sem verificação de estado — dupla baixa destrói a assinatura anterior

ProblemaApp.tsx:396 tem uma única precondição: if (!targetPkg) return;. Verifica existência, não estado. Não há if (targetPkg.status === 'RETIRADA') return;. A escrita em db.service.ts:244 é UPDATE ... WHERE id = ?, sem compare-and-swap.

Cenário reproduzívelPorteiro A e Porteiro B, tablets distintos, mesmo pacote visível. A coleta a assinatura da mãe e confirma. B, com o modal já aberto, coleta a assinatura do filho e confirma. O segundo UPDATE sobrescreve picked_up_by, signature_url, picked_up_at e receipt_protocol. A assinatura de A é destruída. Ficam dois pares de log com destinatários diferentes e uma linha em packages que afirma só o segundo.

Por que a proteção existente não bastaHandoverModal.tsx:316 bloqueia duplo clique local e o filtro de PortariaView.tsx:61-63 some com o item da lista — mas nada disso atravessa dispositivos, e o modal não reage a mudanças no array de pacotes.

CorreçãoUPDATE ... WHERE id = ? AND status = 'ARMAZENADA' com .select(), tratando retorno vazio como "já retirado por outro operador".

ResultadoFAIL

BUG-004 Crítico Integridade · UX

Falhas de banco e de envio são invisíveis — o sistema afirma sucesso

ProblemaToda a camada de dados engole erro: db.service.ts faz console.warn e retorna null/false em fetchUnits, insertPackage, updatePackage e insertLog. Do outro lado, App.tsx:330 chama insertPackage sem await e sem verificar o retorno. O update otimista mantém o item na tela.

Consequência 1Supabase fora do ar é indistinguível de operação normal. O porteiro registra encomendas a tarde inteira vendo toast verde, e nada persistiu.

Consequência 2Quando o fetch falha, App.tsx:154-157 mantém o estado anterior — que são 7 encomendas fictícias de mockData.ts, com fotos de banco de imagens. Elas contam nos KPIs e saem no CSV como dados reais.

Consequência 3PackageIntakeFlow.tsx:279-282 dispara toast afirmando "WhatsApp, E-mail e Push disparados" enquanto as requisições ainda estão em voo.

Correçãoawait nas escritas, verificação do retorno, toast condicionado ao resultado real, e banner de "sem conexão com o servidor" quando o fetch falha.

ResultadoFAIL

BUG-005 Crítico Fluxo 5 · Retirada

QR Code é previsível, não expira, não é consumido — e é dispensável

ProblemaApp.tsx:301 gera o token como QR-B03A102-148800: bloco (público), apartamento (público) e os 6 últimos dígitos de Date.now(). Zero entropia criptográfica — nenhuma chamada a crypto.getRandomValues. Os 6 dígitos cobrem ~16 minutos e são monotônicos; quem sabe aproximadamente quando o pacote chegou (o próprio WhatsApp informa o horário) reduz o espaço a alguns milhares de valores.

Problema maiorNem é preciso adivinhar. PortariaView.tsx:110-123 aceita trackingCode ou id como alternativa ao QR — e o código de rastreio está impresso na etiqueta colada na caixa. Todo o mecanismo de token é contornado digitando um dado visível a qualquer um que passe pela portaria.

Problema 3Encontrado o pacote, o nome do recebedor já vem preenchido com o titular (PortariaView.tsx:120) e é editável livre. A validação exige apenas que o campo não esteja vazio — e ele nunca está. Não há documento, código de confirmação ou qualquer verificação de identidade.

Problema 4Sem expires_at, sem coluna de consumo, sem UNIQUE em qr_token. O badge "QR Code Validado" (PortariaView.tsx:379) aparece mesmo quando o pacote foi selecionado por clique na lista, sem QR nenhum.

CorreçãoToken com crypto.randomUUID(), UNIQUE, expiração, marcação de consumo e validação server-side. Remover trackingCode e id como chaves de retirada.

ResultadoFAIL

BUG-006 Crítico API

Endpoints abertos: gateway de WhatsApp e de e-mail para qualquer pessoa

ProblemaNenhum dos 5 endpoints tem autenticação, verificação de origem ou rate limit.

Impacto — WhatsAppapi/whatsapp/send.ts:36-42 aceita phone e text arbitrários e repassa à Evolution API assinando com a instância oficial do condomínio. É um gateway aberto: golpe do falso boleto e phishing saindo do número verificado do condomínio, com risco de banimento do número.

Impacto — e-mailapi/email/send.ts:31-43 aceita to, subject e html totalmente controlados, com from fixo no domínio do condomínio — SPF e DKIM válidos. Phishing entregue na caixa de entrada com todos os selos de autenticidade, e a reputação do domínio queimada no Resend.

Impacto — Geminiapi/ocr/analyze-label.ts vira serviço de OCR gratuito às custas da cota paga do projeto. Sem limite de tamanho além do limite do Vercel.

Impacto — Evolutionconnect.ts permite forçar reconexão da instância repetidamente (derruba a sessão de WhatsApp do condomínio) e retorna debugRawResponse com o payload cru da API interna.

Nota sobre CORSAusência de cabeçalhos CORS limita chamadas por JavaScript de outra origem no navegador, mas não protege nada: curl e qualquer script server-side ignoram CORS.

CorreçãoExigir JWT do Supabase, validar o papel do chamador, adicionar rate limit por IP, e restringir to/phone aos contatos cadastrados em units. Sanitizar/templatizar o html.

ResultadoFAIL — análise estática; ver §9 sobre a limitação de rede.

BUG-007 Crítico Cadastro · LGPD

Sequestro de unidade: segundo cadastro sobrescreve o morador real

ProblemaQualquer pessoa cadastra, sem autenticação prévia. O id da unidade é determinístico — MoradorRegistrationModal.tsx:203 monta B03-A302 a partir do bloco e apartamento digitados. A única checagem de duplicidade é por e-mail, e só quando o registro existente já tem senha (:176-183).

ConsequênciaDois cadastros no mesmo bloco+apartamento geram o mesmo id, e upsert com onConflict: 'id' (db.service.ts:173) sobrescreve a linha do morador real: nome, telefones, e-mail e hash de senha passam a ser os do segundo. Todas as notificações futuras daquele apartamento são desviadas. Sem aviso, sem confirmação, sem log — handleUpdateUnit (App.tsx:487-499) não gera registro de auditoria.

CorreçãoVincular cadastro a uma validação de titularidade (código enviado pela portaria, ou aprovação do síndico); nunca fazer upsert cego sobre unidade já ocupada.

ResultadoFAIL

05 Bugs de severidade alta

BUG-008AltoModelo de dados

Não existem os estados CANCELADA, DEVOLVIDA e EXTRAVIADA

types.ts:3 e o CHECK em schema.sql:55 reconhecem apenas RECEBIDA, ARMAZENADA e RETIRADA — só o caminho feliz. Uma encomenda extraviada só pode ser fechada de duas formas: registrando uma entrega falsa com assinatura, ou deixando-a pendente para sempre, inflando o estoque e a ocupação de estante. É o pior incentivo possível num sistema cuja finalidade é prova de custódia. E RECEBIDA, dos três, é estado morto: nenhum código o escreve.

BUG-009AltoFluxo 3 · Armazenamento

Localização não tem histórico nem sequer caminho de escrita

packages.shelf é um JSONB com a posição corrente e nada mais. Não há tabela de movimentação. Pior: db.service.ts:231-243 lista 9 campos atualizáveis e shelf não está entre eles — mesmo que a interface oferecesse mover a caixa, não persistiria. Quando o porteiro reorganiza a prateleira fisicamente (rotina diária), o sistema aponta a estante antiga indefinidamente, o morador recebe "Estante A1" no WhatsApp e o pacote está na C3, e o alocador passa a distribuir vagas sobre um inventário que diverge da realidade.

BUG-010AltoFluxo 4 · Aviso

Falha de e-mail é gravada como SIMULATED; FAILED é inalcançável

Seis condições distintas colapsam no mesmo rótulo em resend-email.ts:184: chave ausente no servidor, erro HTTP, recusa da Resend, timeout, offline, rota inexistente. O valor 'FAILED' está declarado em types.ts:130 e é literalmente inalcançável para e-mail. A escolha de palavra agrava: SIMULATED sugere teste deliberado — um auditor descartaria como ruído de ambiente, enquanto investigaria um FAILED.

O mesmo vale para push: web-push.ts:87 grava deliveredAt com timestamp para algo que não foi entregue.

BUG-011AltoAuditoria

Trilha de auditoria é write-only e conta tentativas como sucessos

O estado logs (App.tsx:80) é populado, persistido e nunca passado como prop para componente algum — nem o síndico consegue lê-la pela interface. E o que ela grava é prosa, não dado: sem valor antes/depois, com o campo details sempre null. A descrição do disparo multicanal (App.tsx:374) conta quantas mensagens foram tentadas. Com 3 telefones e todos falhando, o log permanente registra "Disparo Multicanal: 3 WhatsApp(s)".

Pior ainda: App.tsx:435 afirma "com Assinatura Digital e Foto" incondicionalmente, mesmo quando a foto — opcional no modal — não existe. O registro de auditoria afirma um fato que pode ser falso.

BUG-012AltoFluxo 4 · Aviso

Telefone em branco vira (11) 99999-0000 gravado como número real

MoradorRegistrationModal.tsx:200 substitui telefone vazio pelo placeholder e grava no banco como se fosse do morador. A partir daí residentPhones.length > 0 é verdadeiro, o guard de App.tsx:341 passa, e toda notificação daquela unidade vai para um número que pode pertencer a um terceiro — com nome completo, bloco, apartamento e o link de acesso do BUG-002. Não há validação de formato de telefone em ponto algum. Fallback equivalente no e-mail: resend-email.ts:179 usa morador@villageazaleia.com.br como catch-all, para onde vai o comprovante com a imagem da assinatura.

BUG-013AltoFluxo 1 · Entrada

Auto-registro em 2 segundos com nome divergente

resident-matcher.service.ts:162-165 atribui score 86 ao caso "destinatário pode ser dependente"; :245 define alta confiança como score >= 85. O useEffect de PackageIntakeFlow.tsx:118-134 registra sozinho após 2 segundos. Ou seja: o nome não bate e o sistema registra sem clique humano. Combinado com ocr-parser.service.ts:324-329, onde qualquer sequência isolada de 3 dígitos (um CEP, um número de rua, um peso) pode virar o apartamento, a encomenda vai para a unidade errada e notifica o morador errado — e ninguém confirmou nada.

BUG-014AltoRelatórios

Gráfico por bloco perde encomendas silenciosamente

SindicoDashboard.tsx:161-173 deriva os blocos de units, não de packages. Encomenda registrada para bloco sem morador cadastrado — cenário rotineiro, produzido por TotemView.tsx:97 e PackageIntakeFlow.tsx:849 — não aparece em barra nenhuma. A soma das barras difere do total e o gráfico não sinaliza.

BUG-015AltoRelatórios

Presets de data usam UTC — depois das 21h o filtro "Hoje" mostra o dia errado

SindicoDashboard.tsx:84 usa toISOString().split('T')[0], que converte para UTC. Em horário de Brasília (UTC−3), das 21h às 23h59 o preset gera a data de amanhã. O síndico clica "Hoje" às 23h e a encomenda que ele registrou às 22h50 não aparece — o painel exibe zero resultados. Também afeta "Últimos 7 dias" e "Últimos 30 dias", que além disso cobrem 8 e 31 dias por serem inclusivos nas duas pontas.

O filtro manual de datas, por contraste, está correto — a comparação é entre instantes.

BUG-016AltoDuplicidade

Sem unicidade de rastreio em nenhuma camada

packages_tracking_idx (schema.sql:75) é CREATE INDEX, não UNIQUE — e o autor sabia a diferença, porque usou CREATE UNIQUE INDEX na linha 29. Não há checagem no frontend nem no backend. Registrar duas vezes gera duas linhas, duas rodadas de notificação (até 10 mensagens com 5 contatos), duas vagas de estante consumidas — e na retirada o .find() acha só a primeira, deixando a segunda pendente para sempre. Agravante: rastreio vazio vira PKG- + 6 dígitos do timestamp (PackageIntakeFlow.tsx:245), que colide a cada ~16 minutos.

BUG-017AltoPrivacidade

Banner de push expõe dados do morador ao porteiro e ao síndico

App.tsx:334 dispara triggerPushNotification antes de qualquer verificação de contato, alimentando um banner renderizado dentro do AppShell (App.tsx:595) — para qualquer papel logado. O porteiro e o síndico veem nome, transportadora, rastreio e localização de encomenda alheia. Vazamento por design.

Relacionado: assinaturas digitais e fotos de entrega ficam em bucket público (schema.sql:171), legíveis por URL. Assinatura manuscrita é dado biométrico comportamental sob a LGPD.

BUG-018AltoNotificação

Push não é push — é notificação local, inoperante no iOS

web-push.ts:64 usa o construtor new Notification(), que só funciona com a aba aberta em primeiro plano no dispositivo do morador — exatamente o cenário em que push é desnecessário. Não existe pushManager.subscribe(), chave VAPID, endpoint de subscription nem listener de push no service worker (dist/sw.js tem só cache do Workbox). No Safari/iOS o construtor não é suportado: para todo morador com iPhone o canal é 100% inoperante, sempre registrando SIMULATED.

Mesmo assim, PackageIntakeFlow.tsx:730-762 exibe três selos verdes com "✓" — marcas de verificação estáticas, renderizadas antes de qualquer envio.

Não há paginação em lugar nenhum do sistema. PortariaView.tsx:244 usa max-h-80 overflow-y-auto — 320px de altura mostrando ~4 itens, com o DOM inteiro montado por trás. Cada evento Realtime dispara um SELECT * completo na tabela (db.service.ts:205): 20 registros simultâneos produzem 20 varreduras integrais.

Agravante de memória: storage.service.ts:58-62 devolve o base64 original quando o upload falha. Fotos de centenas de KB entram no estado React e no localStorage, estourando a quota do navegador.
